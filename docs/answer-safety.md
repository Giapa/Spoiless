# Answer and citation safety

The backend citation validator accepts a generated JSON answer and the retrieved passages that were supplied to the model. Each citation contains a zero-based passage index and an exact, nonblank quote. A valid result identifies the source section and the quote's character offset. If the response is malformed, an answer is blank or uncited, an index is invalid, or any quote is absent, the entire answer is rejected.

This is only one safeguard. Matching a quote does not prove that the answer's claims are supported, or that the passages are within the reader's current boundary. The caller must retrieve only eligible text, verify the boundary again after generation, withhold results if it changed, and handle insufficient evidence. Do not stream unvalidated output to the reader. The local answer API uses the validator; there is no chat interface yet.

The backend book-answer workflow now combines completed-text keyword retrieval, a model request, and citation validation. It returns a fixed refusal when there is no matching passage or the model reports insufficient evidence. It checks the eligible-text snapshot and watches for database changes before sending text and after generation; any database write causes a conservative retry, including writes unrelated to that book. There remains a small race between the final pre-send check and the network request, and changes during an already-started request cannot retract text already sent. The local answer API uses the selected account, requires a same-origin action and confirmation, and returns no tokens. It does not yet have a chat UI or retain conversation history, and it has only been tested with simulated OpenAI responses. Citation matching and model instructions reduce spoiler risk but cannot guarantee that generated claims are supported or spoiler-free.

The endpoint is `POST /api/books/{book_id}/answer` with `question`, `model`, and `confirm: true`. A successful response contains `answer` and `citations`; recognized usage-limit errors contain a machine-readable code. Responses are not streamed to the browser. The current model must be chosen from the account’s available models; the UI and local model-list endpoint are not implemented yet.
