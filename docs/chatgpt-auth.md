# ChatGPT sign-in groundwork

The project owner reports manually signing in and out with a real ChatGPT account on Linux. Model access, inference, and remote revocation confirmation remain unverified. The offline code in `src/spoiless/chatgpt_auth.py` creates a stable opaque host ID and short-lived authorization attempts, validates a one-time callback, verifies an ID token against a supplied trusted key, and checks the granted plan-use scope. The backend also has a Linux Secret Service credential-store layer and a token-exchange function. A backend-only loopback callback listener has been added. Backend routes can start, cancel and inspect one sign-in attempt, and list and select saved account registrations. The library has a sign-in UI. The single-question interface is wired to inference, but live inference is unverified.

The signed-token verifier currently accepts RS256 only. This is a conservative restriction that must be checked against OpenAI's actual signing keys before enabling sign-in. Tests use locally generated keys, not OpenAI accounts or network access. The OpenAI documentation requires checking the issuer, audience, expiry and nonce and verifying the signature with OpenAI's published JWKS: [registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [identity verification](https://developers.openai.com/siwc/website).

Before enabling this flow:

- The backend-only listener binds to `127.0.0.1` on a temporary port before opening the browser, keeps the attempt in memory, and suppresses callback request logging. Offline tests cover invalid callbacks, expiry, denial and a simulated successful exchange. It is wired to the app UI and supports both new registrations and returning accounts. Cancelling a pending attempt closes the listener; an exchange already in progress may finish.
- The backend exchange uses the documented token endpoint and retrieves signing keys from OpenAI's fixed JWKS URL. It checks the signature and identity before writing credentials to the keyring. It fetches keys on each sign-in rather than caching them, so an unfamiliar key ID gets a fresh lookup. Offline tests use a simulated server and test keys; the project owner also reports a successful real-account sign-in.
- The credential-store layer uses Linux Secret Service directly and fails closed when unavailable. A temporary record was saved, read and removed successfully on this Linux machine on 2026-11-04; other machines and operating systems remain unverified. Keep credentials out of the frontend, logs and library database.
- Connect the store only after verifying the ID token and scope. Handle declined consent and account switching. Backend refresh serializes token read, exchange and write with the same cross-process lock used for sign-in; the store alone does not provide that locking. Local deletion does not revoke access remotely.
- Test an eligible account's end-to-end Responses API flow. A valid identity does not by itself grant plan usage, and account model access has not been checked live.

Each issued client ID has a separate keyring item. A single item contains its token set, and it cannot overwrite a previously stored registration with a different verified subject. Identity-only sign-ins can be stored without granting plan usage. Stored credential fields are omitted from the record's normal representation; callers must still avoid logging the serialized record.

The exchange deliberately disables HTTP redirects and environment-configured proxies to keep authorization codes directed to the documented OpenAI endpoint. This may need revisiting for deployments that require an explicit trusted proxy. The inference adapter is connected to the experimental single-question interface.

The listener's status and account result are backend-only. Avoid logging authorization URLs or callback query strings, ensure a single controlled attempt, and never expose token records to the browser. The project owner reports successful real-account sign-in.

The local sign-in routes accept only loopback requests. Starting or cancelling an attempt also requires a same-origin browser request with an explicit JSON action header; Vite is configured to preserve the browser host when proxying. An OS file lock prevents overlapping sign-in attempts across processes and is held until the callback listener closes. Only status, verified email and plan-permission state can be returned to the app; access and refresh tokens remain in the system keyring.

Account registration metadata (opaque local ID, issued client ID, verified subject and email) and the selected account are stored in the local SQLite database; tokens remain in the system keyring. A registration is recorded after identity verification and before saving tokens, so an interrupted save leaves a recoverable registration. The selected account changes only after storage succeeds, and explicit selection checks that a matching keyring record exists. Switching is blocked during another sign-in, including in a different process. Existing keyring-only records created before this registry are not discovered automatically.

After restart, the backend reports an account as **saved**, not authenticated: token validity and plan eligibility may have changed. The sign-in UI has been tested with simulated backend responses. A local proxy test with a simulated manager confirmed that the Vite configuration allows the app origin and rejects another origin. The project owner reports successful real-account sign-in and sign-out.

For a returning sign-in, the backend resolves an opaque account ID to its saved client ID and expected subject. If the keyring contains the matching registration, the retained ID token is sent as `id_token_hint` in the authorization URL opened in the system browser; it is not returned to the app UI and the URL must never be logged. If no credential remains, the same client ID is used without a hint. The newly signed identity must match before any credential replacement or active-account change. Real returning sign-in and account eligibility remain unverified.

The backend-only token accessor reuses unexpired plan-authorized tokens and refreshes near expiry using the saved issued client ID. The cross-process sign-in lock prevents overlapping refreshes or sign-ins; a concurrent operation receives a busy error and can retry. Confirmed unusable refresh tokens are removed, while temporary failures preserve the saved record. If a successful rotation cannot be saved or its response is lost, the reader may need to sign in again. These paths use simulated OpenAI responses and have not been tested with a real account.

The local sign-out API attempts remote revocation using OpenAI discovery, retries temporary failures, then removes the selected account’s credentials and active selection. It retains the saved account registration for a later sign-in and reports whether remote revocation was confirmed. If revocation was not confirmed, disconnect the app in ChatGPT Settings. Automated sign-out tests use simulated responses; the project owner also reports signing out manually. Remote revocation confirmation was not reported.

The library provides account selection, browser sign-in, cancellation and sign-out. Its first-use plan notice is remembered in browser storage for each local account registration; this marker contains no tokens. Browser tests use simulated responses. The project owner reports signing in and out manually; model access and inference remain unverified.

The backend can request a selected account’s model catalog using its plan-authorized token, refreshing it if needed. It returns only visible model slugs and names in provider order; the app has a model picker and an experimental single-question interface. Catalog tests use simulated OpenAI responses, and live discovery is unverified.

The backend-only inference adapter checks the selected account’s model catalog, then uses the official OpenAI Python SDK to stream a Responses API request with storage disabled. It returns text only after a completed response and reports failures without returning partial text. It is tested with simulated OpenAI responses; no live inference has been verified. The book-answer workflow applies reading-boundary checks and citation validation around this adapter; neither safeguard guarantees spoiler-free output.
